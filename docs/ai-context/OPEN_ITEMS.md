## P1：高价值后续工作

### 3. CI 节流后的 Python 3.13 反馈窗口

额度紧张期间，PR 日常只跑 Python 3.12；Python 3.13 在 `main` 或手动 `workflow_dispatch` 中运行。涉及依赖升级、解释器差异、数据库驱动或打包逻辑的高风险 PR，应在合并前手动跑一次完整矩阵，避免兼容问题延后到合并后才暴露。

### 4. 清理 v15 之外的遗留前端控制器

当前产品壳直接加载 `product-shell-v15.js/css` 和 `light-content-v15.js/css`；v10/v12/v14 及 information-architecture 旧控制器仍在磁盘但不再是 runtime/CI 入口。长期仍会形成理解和维护成本。

后续建议：

- 在浏览器回归覆盖后删除或归档不再使用的控制器；
- 删除重复事件绑定；
- 给关键状态机写浏览器测试；
- 保留一个明确的状态所有者。

在没有完整 E2E 测试前，不要直接删除遗留文件或改变 v15 的状态所有权。

### 5. Minimal Zine 视觉质量继续迭代

当前重构和探针已解决/验证的是：

- 中文和模型图解耦；
- 边缘供应商角标的约束清理（不是绝对预防）；
- 文件路径；
- preview/package 同步；
- 旧图重合成、raw/final 可观测性和 CJK cmap 字体失败闭环。

仍需通过真实题材评估：

- 视觉锚点是否过于通用；
- 每页构图是否有足够差异；
- 旧纸、灰阶和强调色是否符合原 Skill 水平；
- 中文字号、行宽和留白是否适合真实公众号题材；
- 中央区域异常符号的人工检测或自动检测策略；
- GLM 模型随机性及可能再次生成水印/角标的残余风险。

不能把“测试通过”表述成“视觉质量已经达到上游示例水平”。

### 6. 语料池到工作台的产品可见性

批次 anchor 对技术追溯有效，但前端还可以更明确地展示：

- 来源池名称；
- 批次序号；
- 本批详细来源；
- 全池记忆摘要；
- focus；
- pool revision；
- 为什么选中这些来源。

这样用户能理解工作台中的“来源”其实是一次冻结批次。

### 7. 来源规模和性能

来源 API 当前允许拉取较多记录以便前端分组。来源持续增长后，需要评估：

- 后端分页；
- 按平台服务端过滤；
- 虚拟列表；
- 来源缓存失效；
- 语料池重编成本；
- 多个工作台重复请求来源列表。

不要在数据规模尚未测量前盲目微优化，但应保留这一风险。

## P2：长期架构演进

### 8. 统一工作台路由和输入协议

可以考虑稳定的工作台导航事件或 URL state，但必须先有浏览器测试。

### 9. 结构化机器上下文自动生成

当前 `context.json` 由人工维护。未来可增加脚本从 GitHub、Alembic、配置和测试中生成易变化字段，例如：

- 最新 CI；
- 当前 PR head；
- 已注册 router、平台和 Skill。

长期产品原则仍应人工维护，不能全部自动推断。
