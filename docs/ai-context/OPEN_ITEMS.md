- 视觉锚点是否过于通用；
- 同一母题下每页构图是否有足够差异；
- 旧纸、灰阶和强调色是否符合原 Skill 水平；
- 中文字号、行宽和留白是否适合真实公众号题材；
- 中央区域异常符号的人工检测或自动检测策略；
- GLM 模型随机性及中央区域仍可能生成异常文字/水印的残余风险。

V2 的代码范围应只处理 Visual Bible、逐页简报和 distinctness，不回头改 V1 compiler schema；V1 遇到真实 prompt/recipe 差异时应先保存可重放 spec 与 diff，再判断是上游 compiler、页面 brief 还是图片模型问题。

不能把“测试通过”表述成“视觉质量已经达到上游示例水平”。

### 7. 语料池到工作台的产品可见性

批次 anchor 对技术追溯有效，但前端还可以更明确地展示：

- 来源池名称；
- 批次序号；
- 本批详细来源；
- 全池记忆摘要；
- focus；
- pool revision；
- 为什么选中这些来源。

这样用户能理解工作台中的“来源”其实是一次冻结批次。

### 8. 来源规模和性能

来源 API 当前允许拉取较多记录以便前端分组。来源持续增长后，需要评估：

- 后端分页；
- 按平台服务端过滤；
- 虚拟列表；
- 来源缓存失效；
- 语料池重编成本；
- 多个工作台重复请求来源列表。

不要在数据规模尚未测量前盲目微优化，但应保留这一风险。

### 9. 池子记忆效果指标

当前已经有不可变 selection snapshot、角色/阶段使用记录、来源追溯和历史使用次数；它们足以回答“哪些记忆被哪次模型调用消费”。后续若要评估“哪些记忆真的有效”，应基于明确的人类反馈补充：

- 采用、替代和撤销比例；
- 使用记忆后的人工修改率；
- 终稿保留率与重复返工率；
- 按平台、文章类型、风格和角色分组的效果差异；
- 负反馈如何生成新的待批准候选，而不是自动改写正式记忆。

不要从一次生成成功或模型自评推断记忆有效，也不要让效果统计绕过人工批准门禁。
